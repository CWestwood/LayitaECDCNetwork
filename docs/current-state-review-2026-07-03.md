# Layita ECDC Network Current-State Review

Date: 2026-07-03  
Scope: Supabase schema and migrations, Edge Functions, Kobo XLSForm, and representative React/Vite frontend flows.  
Review posture: read-only codebase review focused on data integrity, audit trails, staff access to information, data security, and overall functionality.

## Executive Summary

The application has the main building blocks for a useful NGO monitoring portal: KoboToolbox submissions are logged, processed by Supabase Edge Functions, normalized into ECDC/practitioner/training/visit tables, and surfaced through a React frontend with dashboards, maps, practitioner lists, visit records, audit views, submission monitoring, staff management, and deleted-record handling.

The strongest part of the current design is the intent: raw Kobo payloads are preserved, processing state is tracked, warnings are collected, audit logs are generated by database triggers, and user-facing pages are simple enough for field and M&E staff. The current implementation, however, has several reliability and integrity risks that should be addressed before major new functionality is added.

Top risks:

- The schema source of truth is unclear. `supabase_setup.sql` and the timestamped migrations differ on important objects such as `human_audit_logs`, `kobo_submission_monitor`, `planned_visits`, outreach audit triggers, and some soft-delete behavior.
- The admin reprocessing Edge Function appears broken as written: `reprocess-kobo/index.ts` calls `processPayload(...)`, but the shared module exports `processSubmission(...)`.
- The Kobo form supports outreach values and update flows that the processing function does not fully handle, including `update`, `interested`, and `literacy_promotion`.
- Some hard-delete SQL needs correction before it can be trusted, especially `hard_delete_outreach_visit`, which references `v_deleted_name` without declaring it.
- Some frontend edit/admin flows bypass the documented React Query mutation pattern, use local state for server data, and still use `alert()`/`console.error()` instead of the app's toast/error pattern.
- UI route protection exists, but it should be treated as convenience only. Security must remain enforced by RLS, RPC checks, and Edge Function authentication.

Recommended immediate path: stabilize the schema and backend processing first, then align frontend writes and admin tooling with the documented architecture.

## Current Architecture

### Kobo to Supabase Flow

The intended flow is:

1. KoboToolbox submits a webhook payload to `supabase/functions/kobo-fetch/index.ts`.
2. The function extracts `_uuid` or `_meta.instanceID`.
3. It checks `kobo_processed` and skips only prior `success` submissions.
4. It upserts the payload into `kobo_raw_submissions`.
5. It calls `processSubmission(instanceId, payload)` from `_shared/process-payload.ts`.
6. The shared processor resolves labels, staff, groups, ECDCs, practitioners, training, and visit metrics.
7. It inserts a normalized `outreach_visits` row with `kobo_instance_id` and `source = 'kobo'`.
8. It writes final status, errors, and warnings through `markProcessed(...)`.

The approach is good for auditability because raw payloads and normalized records are both kept. The main gap is that the processing function does not yet match every form workflow in `Kobo form design.xlsx`.

### Supabase Schema

Core operational tables:

- `ecdc_list`: ECDC/site records, area text/area FK, latitude/longitude, chief/headman, child count, attendance timestamp, soft delete in newer migration.
- `practitioners`: practitioner identity, contacts, ECDC/group links, DSD flags, WhatsApp flag, status/group text, soft delete in newer migration.
- `training`: one row per practitioner, with boolean flags for training modules.
- `outreach_visits`: visit log, practitioner/staff links, outreach type, transport, training/book metrics, comments, Kobo provenance fields, source, soft delete in newer migration.
- `planned_visits`: present in the remote schema migration and used by frontend hooks, but absent from root `supabase_setup.sql`.

Kobo and monitoring tables/views:

- `kobo_raw_submissions`: raw JSON payloads keyed by instance ID.
- `kobo_processed`: processing state, errors, warnings, and processed timestamp.
- `kobo_unmatched`: unresolved references for later admin review.
- `kobo_label`: label lookup for Kobo choice lists.
- `kobo_submission_monitor`: view present in the remote migration and used by the frontend monitor.
- `kobotoolbox_ecdc_export` and `kobotoolbox_practitioners_export`: CSV/export views for Kobo external choice lists.

Identity and audit:

- `profiles`: Supabase auth-linked user profile and role.
- `layita_staff`: field staff/data capturer lookup table.
- `audit_logs`: trigger-written JSON field diffs.
- `human_audit_logs`: human-readable audit view present in the remote migration and used by the frontend audit hooks.

### RLS, RPCs, and Audit

The schema uses RLS on public tables and relies on `get_my_role()` for role checks. The design separates read access from admin/manager/datacapturer write access.

Delete behavior is implemented through RPCs in `20260603163351_add_soft_hard_delete_functionality.sql`:

- `soft_delete_practitioner`
- `soft_delete_ecdc`
- `soft_delete_outreach_visit`
- `hard_delete_practitioner`
- `hard_delete_ecdc`
- `hard_delete_outreach_visit`
- `get_deleted_practitioners`
- `get_deleted_ecdcs`
- `get_deleted_outreach_visits`

This is the right pattern for protecting destructive actions, but the implementation needs a focused SQL review before production reliance.

### Frontend

The frontend is React 19, TypeScript, Vite, React Router, TanStack Query, Supabase JS, Leaflet, XLSX, jsPDF, html2canvas, and Sonner.

Primary routes:

- `/dashboard`: KPI/dashboard view.
- `/map`: ECDC map and geographic view.
- `/practitioners`: practitioner list/detail/edit.
- `/visits`: outreach visit list/detail/edit.
- `/audit`: admin audit log view.
- `/kobo-monitor`: admin Kobo submission monitor.
- `/users`: admin staff/profile management.
- `/deleted`: admin deleted-record recycle bin.

The app has route-level protection through `ProtectedRoute` and `AdminRoute`. `Sidebar` also filters admin nav items by `isAdmin`.

## Current Functionality

### Dashboard

`useDashboardStats` fetches counts for practitioners, ECDCs, current-year visits, recent visits, visits by type, visits by staff, visits that did not happen, and mapping visits. It uses `deleted_at IS NULL` filters for the main tables.

Current value: gives NGO staff a compact operational overview.

Attention needed: dashboard calculations happen client-side from fetched rows. This is acceptable at small scale, but as data grows it should move to SQL views/RPCs or paginated/aggregated queries.

### Map and ECDC View

The ECDC hooks fetch ECDCs with coordinates and nested practitioners/training, and filter out soft-deleted ECDCs. The map page supports geographic visualization and staff-friendly filtering/reporting patterns.

Current value: strong entry point for situational awareness.

Attention needed: nested practitioner rows in `useEcdcsWithPractitioners` do not explicitly filter out soft-deleted practitioners in the embedded relationship. Depending on Supabase embedded RLS behavior and active policies, this may or may not be hidden consistently. It should be verified and made explicit if needed.

### Practitioners

The practitioner list fetches practitioner contacts, ECDC, group, DSD flags, WhatsApp flag, training, and related visit stats. It filters `practitioners.deleted_at IS NULL` and excludes deleted visits in global visit stats.

Current value: useful directory and profile surface for staff.

Attention needed: `PractitionerEditForm` directly updates `practitioners` and upserts `training` from the component. It does not use `react-hook-form`, dirty-field payloads, or mutation hooks as described in the design guide. This increases audit noise and makes permission/error behavior harder to standardize.

### Visits

`useVisits` fetches visit date, practitioner name, outreach type, outcome, data capturer, transport, book/training metrics, and comments. Visit detail allows admins/managers to open an edit form after checking the current profile role.

Current value: practical chronological log of field activity.

Attention needed:

- `VisitEditForm` can create a new practitioner while editing a visit. This is a high-integrity action and should be moved into a controlled mutation/RPC with duplicate checks.
- Visit edits write labels such as outreach type labels, while the Kobo processor sometimes stores resolved labels too. The code should define one canonical storage format for coded choice fields.
- The edit permission check happens in UI code, while actual permission depends on RLS. This is acceptable only if RLS is verified and tested.

### Audit

Audit triggers write JSON diffs into `audit_logs` after updates. The frontend reads from `human_audit_logs` and presents recent events.

Current value: good foundation for accountability.

Attention needed:

- Audit currently focuses on updates. Inserts, deletes, raw reprocessing decisions, unmatched resolution, and hard deletes need a clearer audit policy.
- `log_table_updates()` records `auth.uid()`. Server-side Edge Function writes using the service role may produce null or non-human actors unless a service actor pattern is added.
- `supabase_setup.sql` only shows ECDC and practitioner audit triggers, while the remote migration includes outreach and planned visit audit triggers. This drift affects confidence in the audit trail.

### Kobo Monitor

The admin monitor reads `kobo_submission_monitor`, enriches staff/type labels from `kobo_label`, supports search, and expands submission records to show instance ID, data capturer, outreach type, processing time, errors, and warnings.

Current value: very useful operational page for detecting failed or partial syncs.

Attention needed: there is no visible reprocess action wired from the monitor, and the reprocess function appears broken. The monitor is currently more diagnostic than corrective.

### Staff Management

The staff management page shows `profiles` and `layita_staff`, supports search, add, and remove.

Current value: gives admins a basic management surface.

Attention needed:

- Adding `profiles` directly with `crypto.randomUUID()` conflicts with the schema relationship to `auth.users` and is likely to fail or create unusable records.
- Deleting profiles/staff directly can break foreign key constraints or historical attribution.
- This page should be redesigned around Supabase Auth invitations/user lifecycle and staff activation/deactivation rather than raw insert/delete.

### Deleted Records

The deleted records page reads deleted practitioners, ECDCs, and visits through admin RPCs. Hard-delete hooks call RPCs and invalidate affected queries.

Current value: a clear recycle-bin pattern.

Attention needed:

- There is no restore RPC yet, despite the UI language "Contact administrator to restore."
- Hard delete of visits likely fails because the SQL references an undeclared `v_deleted_name`.
- Permanent deletion removes useful historical context and should be rare. For NGO monitoring, a restore-and-archive model is usually safer than hard delete.

## Findings By Principle

### Data Integrity

Critical:

- `reprocess-kobo/index.ts` calls `processPayload(id, raw.payload)` but only imports `markProcessed`; `_shared/process-payload.ts` exports `processSubmission`. Reprocessing failed or partial submissions is therefore likely broken.
- `hard_delete_outreach_visit` references `v_deleted_name`, which is not declared in that function. This likely breaks hard deletion for visits.
- Schema drift between `supabase_setup.sql` and `supabase/migrations` makes it unclear which database shape is authoritative. This affects planned visits, audit views, monitoring views, audit triggers, and soft-delete filtering.

High:

- Kobo form outreach choices include `mapping`, `update`, `caregiver`, and `interested`; the "did instead" choice list includes `literacy_promotion` and `support`. Processing only treats `mapping`, `baseline`, `full_audit` as mapping and `support`, `caregiver`, `literacy` as lookup-only. This means valid form paths may be recorded without the expected ECDC/practitioner/training sync.
- The form field names are nested under groups, e.g. `mapping/area`, `mapping/ecdc_name_link`, `support/parents_present`. The processor expects several of these paths, but not all important fields are captured, including public transport accessibility and people reached.
- Update visits appear to be a major form use case, but the current processor does not have a dedicated update workflow for partial ECDC/practitioner detail updates.
- Direct manual edits in the frontend may overwrite fields without dirty-field tracking, which makes audit logs noisy and increases accidental data changes.

Medium:

- `find_similar_practitioners` does not appear to filter out soft-deleted practitioners in the root SQL. Duplicate warnings may include deleted records unless the latest migration or RLS prevents it.
- `number_children` is stored as text in `ecdc_list`, while the Kobo form treats it as an integer. Counts should be numeric if they drive dashboards and validation.
- `area` exists both as free text and `area_id`; current flows use both patterns. This should be normalized or documented.

### Audit Trails

Critical:

- Source-of-truth drift around audit triggers means it is unclear whether outreach visits are always audited in a freshly built database.
- Hard deletes can remove operational records after writing only a minimal audit entry. This weakens traceability, especially for visits linked to donor/M&E reporting.

High:

- Edge Function writes use service role privileges. The audit trail should explicitly identify "Kobo webhook" or "system processor" as the actor rather than relying on `auth.uid()`.
- The raw Kobo payload is preserved, but transformed field-level decisions and warnings are scattered between `kobo_processed`, `kobo_unmatched`, and normalized rows. A reviewer can reconstruct events, but the workflow is not yet easy.
- Unmatched resolution fields exist, but the frontend does not appear to provide a complete resolve workflow that links unmatched values back into normalized records.

Medium:

- Audit logs are update-focused. Inserts, soft deletes, hard deletes, reprocess attempts, failed reprocesses, and staff/profile changes should have consistent audit coverage.
- Frontend edit forms do not consistently send only changed fields, so audit logs may show broad updates.

### Ease of Access for NGO Staff

High:

- The dashboard, map, practitioner directory, visits list, audit page, and submission monitor cover the right information needs, but corrective workflows are incomplete. Staff can see issues like partial submissions, but may not be able to resolve them from the app.
- Staff management exposes low-level database concepts (`profiles` vs `layita_staff`) rather than the staff workflow: invite user, assign role, link data capturer identity, deactivate/reactivate.

Medium:

- Several pages use legacy CSS/classes and inline styles. The UI is functional, but consistency may degrade as more features are added.
- Some loading/error states are present, but errors are not always standardized with Sonner toasts or reusable components.
- The app currently assumes all authenticated users can read most operational data. This may be acceptable for a small NGO, but it should be a deliberate policy.

Low:

- The dashboard uses "this year" based on the browser date. This is simple, but reporting periods may need configurable NGO/donor periods later.
- Some labels use technical terms such as "Hard Delete"; staff-facing language could be softened and clarified.

### Data Security

Critical:

- Security must not rely on hidden admin nav items or frontend role checks. The current code has UI checks, but RLS/RPC/Edge Function checks need automated verification.
- The webhook function accepts JSON and uses the service role. There is no visible request authentication, shared secret, signature validation, or origin check in `kobo-fetch/index.ts`. If the function URL is exposed, unauthorized submissions could be inserted.

High:

- The reprocess Edge Function uses a bearer token and profile role check, which is the right idea, but the broken processor call means it cannot yet be trusted operationally.
- `StaffManagement` attempts direct profile insert/delete. User lifecycle should happen through Supabase Auth/admin APIs or controlled server-side functions, not arbitrary client-generated profile IDs.
- Broad read policies expose operational data to every authenticated user. If roles such as `library` or `datacapturer` should have narrower access, RLS needs tightening.

Medium:

- Raw Kobo payloads may contain personal information, phone numbers, comments, and photo metadata. Only administrators can read `kobo_raw_submissions`, which is good, but retention and export policies should be defined.
- Frontend forms fetch all practitioners/ECDCs for selection in some edit flows. This is convenient, but it means access policy should be reviewed against privacy expectations.

### Overall Functionality and Performance

High:

- Build/test status was not run during this review to avoid creating build artifacts. A build/lint pass should be part of the stabilization work.
- Some code comments indicate temporary debugging, e.g. `console.log('QueryClient:', client)` in `useEcdcsWithPractitioners`.
- Direct Supabase calls from components make cache invalidation inconsistent. Some edits call `onSaved`, but do not necessarily invalidate React Query caches at the hook level.

Medium:

- Dashboard stats and visit summaries fetch potentially growing datasets and aggregate client-side.
- No automated tests were found in the inspected frontend/backend paths. Core flows need regression coverage before adding major features.
- TypeScript is mixed with JavaScript (`supabaseClient.js`, utility files), and several components use `any`. This lowers confidence in refactors.

## Suggested Improvements

### Critical

1. Establish one database source of truth.
   - Decide whether migrations or `supabase_setup.sql` is authoritative.
   - Regenerate or reconcile the non-authoritative file.
   - Confirm `human_audit_logs`, `kobo_submission_monitor`, `planned_visits`, soft-delete columns, export views, and audit triggers exist in the intended production schema.

2. Fix and test the reprocess flow.
   - Import/call `processSubmission` consistently.
   - Add admin-only reprocess tests for success, partial, failed, and missing raw payload.
   - Surface reprocess from the Kobo monitor only after the backend is verified.

3. Add webhook authentication.
   - Require a shared secret/header or equivalent Kobo-compatible authentication.
   - Reject unauthenticated webhook calls before writing raw payloads.
   - Log unauthorized attempts separately from normal failed processing.

4. Repair hard-delete SQL before use.
   - Fix `hard_delete_outreach_visit`.
   - Verify all hard-delete RPCs compile and behave correctly.
   - Prefer restore/archive flows over hard delete for routine admin use.

### High

1. Align Kobo XLSForm workflows with processing logic.
   - Add explicit handling for `update`, `interested`, `literacy_promotion`, and "did instead" support/literacy paths.
   - Decide the canonical stored value for choice fields: Kobo code or human label.
   - Capture currently ignored but useful fields such as public transport accessibility and people reached, if needed for reporting.

2. Strengthen audit policy.
   - Audit inserts, soft deletes, hard deletes, reprocess attempts, unmatched resolutions, and staff/profile changes.
   - Add a system actor convention for service-role Edge Function writes.
   - Ensure outreach visits and planned visits are audited in every schema path.

3. Replace direct frontend writes with mutation hooks or RPCs.
   - Move practitioner, training, visit, staff, and profile writes out of components.
   - Use dirty-field payloads to reduce accidental updates and audit noise.
   - Standardize mutation success/error feedback with Sonner.

4. Redesign staff/profile management.
   - Treat `profiles` as auth-linked records only.
   - Add invite/deactivate/reactivate role workflows.
   - Link `profiles` and `layita_staff` explicitly instead of relying on matching names.

5. Add restore functions.
   - Add admin RPCs to restore soft-deleted practitioners, ECDCs, and visits.
   - Keep hard delete available only for exceptional cleanup.

### Medium

1. Add automated regression checks.
   - SQL migration smoke test.
   - Edge Function unit tests with sample Kobo payloads.
   - Frontend build/lint/type checks.
   - RLS policy tests for administrator, manager, datacapturer, library/viewer-like roles.

2. Move dashboard aggregation server-side as data grows.
   - Use SQL views/RPCs for annual counts, staff counts, recent visits, and mapping progress.
   - Keep frontend hooks focused on rendering already-aggregated data.

3. Normalize data types and naming.
   - Convert child counts to numeric fields where possible.
   - Clarify `area` text vs `area_id`.
   - Add consistent indexes for common filters: date, practitioner, ECDC, group, deleted status, processing status.

4. Complete unmatched-resolution workflow.
   - Let admins resolve `kobo_unmatched` rows.
   - Reprocess or patch affected visits after resolution.
   - Audit who resolved each unmatched record and when.

### Low

1. Remove temporary debug output and stale comments.
2. Standardize empty/error/loading states across pages.
3. Replace staff-facing technical labels like "Hard Delete" with clearer admin language.
4. Consider configurable reporting periods beyond calendar year.
5. Continue consolidating legacy components/styles into feature modules.

### Kobo Form Mapping Notes

The workbook has `survey`, `choices`, and `settings` sheets. Survey rows include:

- Core fields: `outreach_date`, `data_capturer`, `outreach_type`, `happened`, transport fields, comments.
- Practitioner/ECDC lookup fields: `ecdc_practitioner`, `practitioner_new`, calculated ECDC/practitioner fields from external CSVs.
- Mapping group: `mapping/area`, `mapping/ecdc_name_link`, `mapping/ecdc_name_link_new`, contact fields, `mapping/location`, DSD fields, chief/headman, child count, training, photo.
- Support group: `support/parents_enrolled`, `support/parents_present`, BookDash metrics.

Choice values include:

- `outreach_type`: `mapping`, `update`, `caregiver`, `interested`.
- "Did instead" values: `literacy_promotion`, `support`.
- Groups: `ss_1` through `ss_6`, `ss_interested`, `ss_not_trained`, `ss_other`.
- Training choices: `firstaid`, `level4`, `level5`, `other`.

Main mismatch: the processor currently recognizes more/other internal outreach types (`baseline`, `full_audit`, `support`, `literacy`) but does not explicitly handle all current workbook values.
